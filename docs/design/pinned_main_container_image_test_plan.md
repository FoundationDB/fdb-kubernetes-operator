# Test Plan: Pinned Main Container Image

Companion to [pinned_main_container_image.md](pinned_main_container_image.md). It lists what should be tested, at which
level, and what is already covered. Status: **Done** = exists, **Gap** = not tested yet.

Terminology: `M` is `monitorVersion`, "capable Pod" is a Pod that uses the shared binary launcher (`--version-file`, no
`--main-container-version`), "in place" means no Pod is recreated.

## 1. How to verify the key claims

These checks are used by the e2e tests (and partly by the controller tests):

| Claim | How to verify |
|---|---|
| Pod was not recreated | Compare Pod UID and `creationTimestamp` before and after; compare container restart counts of the main container |
| Sidecar was updated in place | Sidecar image changed, sidecar restart count +1, main container restart count unchanged |
| Right binary is running | `command_line` of the process in the machine-readable status starts with `/var/fdb/shared-binaries/bin/<version>/fdbserver`, or `/usr/bin/fdbserver` when running the baked-in binary |
| Right version is running | `version` of every process in the status equals `spec.version` |
| Binaries are staged | `ls /var/fdb/shared-binaries/bin` in the sidecar contains `<version>/fdbserver` and `fdbcli` |
| No unnecessary recovery | Recovery count / `generation` of the recovery state before and after; at most one recovery for an in-place upgrade |
| Data is available | Write and read keys through the upgrade (`loadData: true`), check client errors and availability |
| Mode is honored | Process command line / `BINARY_DIR` and running version after the bounce |

## 4. E2E tests

Proposed location: extend `e2e/test_operator_upgrades_variations` (reuse `performUpgrade`) or a new package
`e2e/test_operator_pinned_main_image`. Note: the table that is already in the working tree uses `FDescribeTable`, which
focuses the test and must become `DescribeTable` before it is committed.

Add fixture helpers first:
* snapshot of Pod UIDs / creation timestamps / restart counts and an `AssertPodsNotRecreated`,
* `GetProcessBinaryPaths` from the status, `GetStagedVersions` through an exec into the sidecar,
* recovery counter snapshot.

### 4.1 Core scenarios (must have)

| ID | Scenario | Expected |
|---|---|---|
| E1 | Enable the pin (`M = spec.version`) on a running cluster | No Pod recreated, cluster reconciles, processes use the baked-in binary |
| E2 | Version incompatible upgrade with the pin (for example 7.3 → 7.4) with `loadData` | No Pod recreated, main image unchanged, sidecar new, processes run `bin/<new>/fdbserver`, versions equal `spec.version`, data intact, at most one recovery |
| E3 | Patch upgrade inside the pinned minor, twice in a row | First upgrade recreates the Pods and they are capable. Second upgrade: no Pod recreated, processes run `bin/<new>/fdbserver`, one restart |
| E4 | Chain: pin at A, incompatible to B, patch to B', incompatible to C | No Pod recreated after the first capable state, correct binaries, `bin/` contains all staged versions |
| E5 | Roll the pin forward: `M` and `spec.version` set together (patch and incompatible) | Normal rolling update, new Pods have the new main image and run the baked-in binary, following upgrade is in place |
| E6 | Change only `M` | Rolling update to the new main image, FDB version unchanged |
| E7 | Unset `monitorVersion` | Rolling update back to `spec.version` images, no stuck state, ConfigMap key removed |
| E8 | Operator upgrade with an unpinned cluster (existing operator upgrade test) | No Pod recreated, specs and hashes unchanged |

### 4.2 Failure and robustness scenarios

| ID | Scenario | Expected |
|---|---|---|
| E9 | Delete a Pod during an in-place upgrade (before and after the sidecar patch); also every Pod that is newly created by the first patch upgrade (found a stuck cluster in a manual e2e run, see the cold start note in the design) | The new Pod starts, stages the binary, its fdbserver starts on the right version without manual action (**cold start gap**: measure the time and check that the launcher is not stuck) |
| E10 | Kill the sidecar container and the main container during the bounce | The upgrade completes |
| E11 | Restart the operator during an in-place upgrade | The upgrade completes, no Pod is recreated |
| E12 | Chaos from the existing upgrade-with-chaos suite (pod kill, network partition, node failure) while upgrading in place | The upgrade completes, no data loss |
| E13 | Replace a process group / scale up / scale down after the upgrade | New Pods get the pinned main image and the new sidecar and work |
| E14 | Node drain after the in-place upgrade | Pod is recreated with the right spec and runs the right version |
| E15 | Sidecar fails to stage the binary (crash-loop the sidecar through the buggify option) | The bounce does not happen, the cluster keeps running the old version, recovery after the sidecar is healthy |

#### Stragglers that miss the restart (incompatible upgrades)

In the default mode, every incompatible upgrade ends with a recreation of all Pods, which also restarts a process that
missed the kill. With a pinned image that safety net is gone. The existing `removeIncompatibleProcesses` reconciler
(`--enable-restart-incompatible-processes`, on by default) recreates Pods of processes that show up in
`incompatible_connections`, but it needs a status from the database and `!IsBeingUpgraded()`.

`spec.buggify.ignoreDuringRestart` skips the kill for the listed process groups and is the simplest way to create
stragglers in an e2e test.

| ID | Scenario | Expected |
|---|---|---|
| E27 | Incompatible upgrade with `ignoreDuringRestart` for one storage process group (database stays available) | The straggler is detected through `incompatible_connections` and its Pod is recreated, the new Pod starts the new version from the staged binary, the cluster is fully reconciled. Record the time until the straggler is gone |
| E28 | Same, but for enough coordinators that the cluster controller cannot be elected, or for a log quorum, so that the database is unavailable | Document what happens: whether the status is still available, whether `removeIncompatibleProcesses` runs, how long it takes, and what the manual recovery is (delete the Pods or toggle the isolate annotation) |
| E29 | Same as E27 with `ignoreDuringRestart` for a process group of a stateless and a log class | Same as E27, no data loss |

Not covered yet: a restart of stragglers that does not depend on the status of the database. This needs the monitor to
report the version of the running processes (an addition to `STAGED_VERSIONS` in the environment annotation) and an
operator step that uses it. The operator step is **deferred** until a monitor release contains the change, so E28 is
expected to document a limitation and not to pass without manual recovery.

### 4.4 Tooling and limits

| ID | Scenario | Expected |
|---|---|---|

## 5. Exploratory / manual checks before the first release

* Behavior with a real Kubernetes ConfigMap sync delay: the capable Pod mounts the `shared-binary-version` file before
  the ConfigMap contains the key (mount error, Pod stuck in `ContainerCreating`). Check the ordering of `updateConfigMap`
  and Pod creation.
* `kubectl describe` output of an upgraded Pod: container args and volumes are as documented.
* Upgrade with an operator that has a different `ImageConfigs` set than the one that created the Pods.
* Behavior of the pinned cluster in `operator --print-version` / metrics (`running_version` versus `desired_version`).

## 6. Suggested order

1. Unit gaps in 2.1–2.4 (cheap, mostly table tests).
2. Controller gaps: downgrade, unset, `PodUpdateStrategy`, operator restart, mid-upgrade Pod creation.
3. E1–E3 and the fixture helpers, then E5–E8.
4. E9–E15 (this is where the cold start gap is validated).
5. E16–E26.
