# Description

Allow users to expire old backup data on a recurring schedule through `FoundationDBBackup.spec.expiration`, using [`fdbbackup expire`](https://apple.github.io/foundationdb/backups.html#expire):

```yaml
spec:
  expiration:
    expireAfterSeconds: 2592000
    restorableForSeconds: 604800
    intervalSeconds: 3600
```

Use `restorableAfterVersion` instead of `restorableForSeconds` to protect an external checkpoint. FDB's default check can pass when a newer snapshot survives but an older checkpoint loses its required snapshot. The checkpoint owner supplies and advances the oldest required version.

## Type of change

- New feature (non-breaking change which adds functionality)

## Discussion

Each Job captures the current destination, cutoff, and restore requirement in its arguments, without `--force` or encryption flags. Replacement waits for the previous Job and its Pods; failures use persisted exponential backoff. Expiration progress lives in `status.expiration` independently of backup reconciliation.

Runs default to hourly, with configurable Job polling. Backup retries and Pod cleanup retain their own deadlines.

Suggested review order: API and validation, Job construction in `internal/backup_expiration.go`, then scheduling and cleanup in `controllers/expire_backup.go` and `controllers/backup_controller.go`. The CRD, apply configurations, deepcopy code, and API reference are generated.
